## Claim flow and security boundary

1. Captain opens `/activate-legacy`, chooses a new password and requests a Supabase Auth account. No legacy hash is read or copied, and no teamDraft or privileged metadata is submitted. New/existing address-dependent responses receive a neutral receipt that does not assert delivery. Infrastructure failures remain errors. Existing new-system accounts use login or normal password recovery.
2. Captain confirms their email using the existing `/verify-email` TokenHash flow and logs in through secure cookies. Signup confirmation must be enabled in Supabase. Confirmation alone never grants team ownership.
3. `/account/legacy-claim` submits the legacy team number. Known/unknown numbers receive the same 202 receipt; duplicate submissions do not create another request. Users see only their own request receipts. A confirmed account without a team may use this route.
4. A support-moderator or super-admin opens `/admin/legacy-claims`, checks the original private contact against independent ownership evidence, records its case UUID, and confirms the review. Applicant email/name matching is insufficient. Self-review, unavailable holding, missing original contact and stale versions are rejected. Other administrator roles cannot approve through UI, API or direct RPC.
5. Approval returns a cryptographically random 256-bit code **once** to that reviewer. Only its SHA-256 digest is stored. The reviewer manually delivers it through the independently verified **original** contact channel. Do not deliver to a newly supplied channel based on the application request. No automated claim-email delivery is implemented. Never put the code in a URL, case notes, analytics, logs, screenshots or public notifications.
6. Code expires after 30 minutes and is bound to one request and Auth UUID. Reissue rotates the digest and requires current version; rejection revokes it. The confirmed claimant redeems it. Holding/request row locks and an Auth-row lock serialize competing team and account claims. Ownership creation, consumption, rival-request rejection and audit commit together. Invalid redemption attempts persist rate counters/audit without transferring ownership.
7. Original name, mapped approval state (including bans/rejections), rejection reason and creation date survive claim. Ownership does not confer approval or lift a ban. Real PUBG IDs and roles are supplied separately by the verified owner for the five preserved names. No captain role is inferred from slot order. Existing roster/registration locks and unique identities apply; roster completion is atomic and one-time.

Holding and challenge tables have RLS and no direct PUBLIC/anon/authenticated/service-role grants. Caller-JWT security-definer RPCs enforce confirmed identity and narrow roles; ordinary mutations never use service-role identity. Only the existing rate-limit helper uses the server service client. Codes are not returned to claimants through list endpoints. Account changes remount protected content and invalidate private caches using the existing architecture.

Limits: activation 5/IP/minute and 3/normalized-email/hour; request 10/IP/minute plus 5/account/hour; redemption 20/IP/minute plus 10/account/hour; reviews and roster completion 10/account/hour. Existing Auth recovery limits remain. Auth provider limits also apply. RPC attempts cannot bypass the account limit; invalid code failures persist audit entries. Monitor abuse using redacted event metadata.
